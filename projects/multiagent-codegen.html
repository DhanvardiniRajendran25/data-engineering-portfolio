A preprocessing prompt-injection hardening layer and an automated evaluation harness complete the pipeline.

System Architecture

How a request becomes code

Three agents in a strict linear pipeline, with a security check at input and an evaluation harness at output. The Planner-first design is the key architectural choice: no code is generated until a structured plan is approved.

Agent Roles

Three agents, one responsibility each

Planner Agent

Receives the raw user request and decomposes it into a structured implementation plan: subtasks in dependency order, function signatures, data types, edge cases to handle, and explicit constraints (no external libraries, no side effects, etc.). The Planner output is a specification document — the Coder works from the spec, not from the raw request. This is the core design choice that reduces hallucination.

Coder Agent

Takes the Planner's spec and generates code subtask by subtask, in the order defined by the plan. The Coder has a limited context window per subtask — it sees the spec, the current subtask, and the already-completed code. This constraint forces modular output that the Reviewer can check incrementally rather than reviewing one large block of code.

Reviewer Agent

Runs three checks on the Coder's output: (1) correctness — does the code match the Planner's spec? (2) quality — are there logic errors, edge cases not handled, or performance issues? (3) security — are there injection vectors, hardcoded credentials, or unsafe operations? On failure, the Reviewer sends the code back to the Coder with specific revision instructions.

Evaluation Harness

After the Reviewer approves, an automated test suite runs against the output: unit tests for the requested functionality, edge case tests generated from the Planner's constraints, and a regression suite to catch changes that break previously-passing behavior. Output is only released if all harness tests pass.

Key Decisions

Why it was built this way

Decision 1

Planning-first architecture: Planner before Coder. Direct code generation from a raw user request is the primary cause of hallucination and spec drift in code-generation systems. The Planner produces a structured intermediate representation — a spec — that the Coder follows exactly. Hallucination is dramatically reduced because the Coder is implementing a known spec, not interpreting a vague request. It also makes the system easier to debug: if the output is wrong, you can immediately check whether the Planner's spec was wrong or the Coder deviated from it.

Decision 2

Dedicated Reviewer agent instead of self-review. Self-review (asking the same LLM that generated the code to also check it) has a well-documented failure mode: the model tends to validate its own output rather than critique it. A separate Reviewer agent, given only the spec and the code, is more likely to surface genuine errors because it has no prior commitment to the code it's reviewing.

Decision 3

Prompt injection hardening at preprocessing, before the agent pipeline starts. In a code generation system, a prompt injection attack can cause the Planner to produce a spec that generates malicious code, which the Coder implements and the Reviewer may miss. Catching injections before any agent sees the input prevents the entire downstream pipeline from being compromised — it's far cheaper and more reliable than asking each agent to individually detect and resist injections.
