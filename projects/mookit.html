System Architecture

Four tiers, one security model

Every request travels through all four tiers. No layer can bypass the next — the database rejects calls that don't come through stored procedures, and the API rejects requests that don't pass RBAC.

Layer Breakdown

What each tier does

Frontend — React

Product catalog with filter/sort, cart, JWT-authenticated checkout flow, and order tracking. All API calls include the JWT access token in headers. No database credentials or connection strings exist in the frontend — all data operations go through the Express API.

API — Express.js + RBAC

Every route is protected by RBAC middleware that checks the JWT role claim against a permissions matrix. Admin routes, customer routes, and reporting routes have separate permission sets. Input validation runs before any database call — malformed inputs are rejected at the API boundary, not at the database.

Database — SQL Server

All data operations (reads, writes, updates, deletes) go through stored procedures. No ad-hoc SQL is executed against the database. Audit triggers log every INSERT, UPDATE, and DELETE to an immutable audit table with timestamp and actor. AES-256 encryption is applied at the column level on all PII fields (name, email, address, payment info).

Analytics — Power BI

Power BI connects to SQL Server read-optimized views — not directly to the base tables. Views enforce the same column-level access control as the API layer. Dashboards cover: sales trend by product category, inventory turnover rate, customer cohort segments, and order fulfillment SLAs.

Key Decisions

Why it was built this way

Decision 1

Stored procedures for all data operations. Ad-hoc SQL from application code is the most common vector for SQL injection — even with parameterized queries, the surface area is large. Stored procedures encapsulate all data operations inside the database, centralizing business logic and reducing the attack surface to a known set of named procedures. They also enable DB-level auditing that the application layer can't intercept.

Decision 2

AES-256 at the column level for PII fields. Encrypting at the application layer before writing to the database means the data is protected even if the database host is compromised — the attacker gets ciphertext, not plaintext. Field-level encryption (vs. full-disk encryption) also allows selective decryption: analytics queries on non-PII columns run without ever touching the encrypted fields.

Decision 3

RBAC at both API and database layers. A single RBAC layer at the API is insufficient — if the API is bypassed (direct database connection, compromised service), there is no secondary control. Enforcing access control at both layers means an attacker who gets past the API still hits a second enforcement point at the stored procedure level.
