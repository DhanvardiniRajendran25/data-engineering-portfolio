Pipeline Architecture

From policy PDF to cited answer

Three distinct pipeline concerns: ingest-and-index, retrieve-and-reason, and output-with-guardrails. Each is independently replaceable — swap the vector store, change the LLM, or add a new guard layer without touching the others.

Stage Breakdown

What happens at each step

Ingest & Index

Policy PDFs are chunked at 512 tokens with 64-token overlap — overlap ensures no sentence is split across a chunk boundary. Each chunk is embedded with text-embedding-ada-002 and stored in ChromaDB. A parallel BM25 index is built for sparse keyword retrieval. Both indexes are built once and updated incrementally when policies change.

Hybrid Retrieval

User query triggers both retrieval paths: ChromaDB dense search (semantic similarity) and BM25 sparse search (keyword match). Results are merged and reranked using a cross-encoder before the top-k chunks are passed to the reasoning agent. Dense search misses exact policy numbers; BM25 catches them — the union beats either alone.

LangGraph ReAct Reasoning

A ReAct (Reason + Act) agent loop: the agent retrieves chunks, reasons about them, identifies if additional retrieval is needed (e.g., detecting a cross-referenced section), and iterates until it can synthesize a complete answer. This loop is what enables policy-conflict detection — a single-shot prompt can't compare multiple documents iteratively.

Guardrails & Output

A preprocessing prompt-injection shield analyzes each user query before it reaches the retrieval stage. Injection attempts are detected and blocked with a 100% block rate on the test set. GPT-4o generates the final answer with explicit policy citations, a confidence level, and a risk label (Low/Medium/High) based on the retrieved policy language.

Key Decisions

Why it was built this way

Decision 1

Hybrid RAG (dense + sparse) over vector-only retrieval. Pure vector search is excellent for semantic similarity but fails on exact policy identifiers — a question about "Policy HR-204" won't match the policy document semantically if the embedding doesn't weight exact strings. BM25 catches these exact matches. The hybrid approach, with reranking, consistently outperforms either retrieval method in isolation on policy QA tasks.

Decision 2

LangGraph ReAct over single-shot prompting. Policy conflict detection requires comparing multiple documents iteratively — a single prompt with all retrieved chunks can't do this reliably. The ReAct loop lets the agent retrieve from one policy, identify a potential conflict, retrieve from a second policy, compare them explicitly, and then synthesize a final answer. This iterative structure produces measurably better accuracy on conflict-detection queries.

Decision 3

Prompt injection shield at preprocessing, not at the LLM layer. Relying on GPT-4o to refuse injection attempts is slower and more expensive than detecting them before the query reaches retrieval. Preprocessing detection runs a lightweight classifier on the raw user input — blocked queries never touch the vector index or the LLM, reducing cost and eliminating the risk of jailbreaks that bypass LLM-level refusals.
