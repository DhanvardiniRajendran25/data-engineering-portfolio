Pipeline Architecture

How the data flows

Profile first, clean second, model third, load with a watermark, serve from the warehouse. Each stage has a clear contract with the next.

↓

Stage Breakdown

What happens at each step

Profile

ydata-profiling generates a full statistical report on the raw CSV before any transformation: null percentages per column, value distributions, high-cardinality warnings, and encoding anomalies. No SQL was written until this report was reviewed.

Clean

Alteryx workflows standardize borough codes (borough abbreviations → full names), fix date format inconsistencies across different arrest years, and resolve null perpetrator demographics with sentinel values — all with visual, auditable transformation steps.

Model

ER Studio dimensional design: ARREST_FACT + four dimensions — LOCATION_DIM, PERPETRATOR_DIM, OFFENSE_DIM, DATE_DIM. SCD Type 2 applied to LOCATION_DIM (precinct boundaries change) and PERPETRATOR_DIM (case details evolve), preserving full history.

Incremental Load

ADF pipeline uses a watermark table to track the last-processed modification date. On each run, only rows newer than the watermark are pulled and loaded — avoiding full table scans on a growing arrest dataset. Watermark is updated atomically after each successful load.

Key Decisions

Why it was built this way

Decision 1

SCD Type 2 on Location and Perpetrator dimensions. NYPD precinct boundaries change, and case details (charges, dispositions) can be updated after initial entry. Type 2 creates a new row for each change with effective dates, so historical arrest records always join to the correct historical dimension row — not the current one.

Decision 2

Watermark-based incremental loads over full refreshes. The NYPD dataset grows continuously. A full reload every run would scan millions of rows unnecessarily. The watermark pattern tracks the last-processed timestamp and pulls only new or changed rows, keeping load times predictable as the dataset scales.

Decision 3

Profile before modeling. Running ydata-profiling before writing a single transformation caught three encoding issues and two columns with >40% nulls that needed sentinel handling. Discovering these in profiling instead of in production saves the much more expensive fix of backfilling a live warehouse.
