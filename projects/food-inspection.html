Stage Breakdown

What happens at each layer

Bronze — Raw Ingest

Chicago and Dallas CSVs land in Azure Data Lake as-is. No schema enforcement, no transformation. Auditability columns (job_id, load_dt, source) are appended at this stage and carry through every downstream layer, making every record traceable to its origin job and timestamp.

Silver — Chicago

Chicago stores all inspection violations as a single unstructured string per record. PySpark regex parsing splits that string into structured violation records: violation code, description, comment — one row per violation. Without this step, violations are not queryable at all.

Silver — Dallas

Dallas uses a wide format with 25 separate boolean columns for each inspection type. PySpark unpivot (stack()) converts the wide format to a normalized long format: one row per inspection type per record. This schema can then be unioned with Chicago's data without column explosion.

Gold — Dynamic Tables

Snowflake Dynamic Tables define the Gold layer declaratively: they recompute automatically whenever upstream Silver data changes. No scheduled jobs, no manual refresh triggers. Tableau reads directly from Dynamic Tables — always current, never stale.

Key Decisions

Why it was built this way

Decision 1

Snowflake Dynamic Tables over scheduled tasks for Gold. Dynamic Tables are declarative — they define what the output looks like, not when to recompute it. Snowflake tracks upstream dependencies and triggers incremental refresh automatically. This eliminates an entire class of "stale dashboard" bugs that come from scheduled tasks that run too rarely or fail silently.

Decision 2

Regex violation parsing on Chicago data. The source schema stores all violations for an inspection as a single concatenated string — a common "legacy CSV" antipattern. Leaving it as-is makes violations impossible to filter, group, or aggregate. PySpark regex parsing was the only viable option to make the data analytically useful without modifying the source system.

Decision 3

Auditability columns (job_id, load_dt, source) on every record from Bronze onward. In a multi-city pipeline with two distinct sources, tracing a bad record back to its origin job and load time is critical for debugging. Adding these at Bronze — not Silver or Gold — means every downstream transformation carries the lineage tag automatically.
